## 2026-11-03 – Fixed a real Azure-restore bug: the sha256 check was order-sensitive

**Generated:**
- `services/backup.py`'s `_components_hash()` now sorts the given components by `id` before hashing, making the hash invariant to the list's order rather than just its content.

**Root cause (live-reported: a backup to Azure succeeded, and the downloaded file visibly had the right data, but restoring it failed with "sha256 hash does not match"):** `export_snapshot()`'s hash is computed over `db.query(Component).order_by(Component.id)` -- a single list ordered by id, mixing every category together in insertion order. `_write_xlsx` then groups those same components into one sheet per category (CPU sheet, motherboard sheet, ...) for human readability, and `_read_xlsx` reconstructs the list by reading sheet-by-sheet in `Category` enum order (CPU, MOTHERBOARD, RAM, GPU, STORAGE, PSU, CASE, COOLER) -- a completely different order whenever the inventory's insertion order doesn't happen to already match that exact sequence. `json.dumps(..., sort_keys=True)` only sorts each dict's own keys; it never reorders the list itself, so any multi-category inventory whose components weren't inserted in that one specific order would hash differently after the round-trip, despite nothing being corrupted. This bug has existed since the `.xlsx` format itself was introduced (2026-10-31's entry) -- it was never caught earlier because every existing test's hand-crafted inventory happened to insert components in (or close enough to) `Category`'s own enum order, and the Azure path had never actually been exercised against a real account with a real, large inventory until now (flagged as a known gap in an earlier readiness review).

**Assumptions:**
- **Fixing the hash function itself, not `_write_xlsx`/`_read_xlsx`'s sheet grouping.** Reordering the xlsx reader to reconstruct the original id order was considered, but the hash's actual job is verifying *content* integrity, not row order -- a tamper check that happens to also enforce a specific row order is stricter than it needs to be, and was the actual source of this false positive. Sorting inside `_components_hash` fixes the real problem at its root and is a one-line, obviously-correct change, versus making the xlsx reader reconstruct an ordering it has no real need to preserve.

**Known risks / weaknesses:**
- None specific to this fix -- it tightens an existing check to be strictly more correct (fewer false positives) without weakening what it actually verifies (every component's content still has to match exactly, still via a cryptographic hash).

**Tests covering it:**
- `backend/tests/test_backup.py` (1 new test): components inserted in an order deliberately different from `Category`'s own enum order (PSU, then CPU, then GPU, then motherboard) round-trip and restore successfully. Verified this test actually fails with the old code (reverted the fix locally, confirmed the exact same "sha256 hash does not match" error the student hit, then reapplied the fix) before trusting it as a real regression test, not just a passing assertion.
- Re-ran the full 210-component real seed data through `export_snapshot` → `_write_xlsx` → `_read_xlsx` → `_components_hash` end to end and confirmed the hash now matches (previously confirmed to mismatch with the same data before this fix).
- `ruff check`/`ruff format --check`/`pytest --cov` green: 222 tests, 96% overall coverage.

## 2026-11-02 – Deliberately diversify the suggested builds (not just swap minor parts)

**Generated:**
- `pipeline/recommend.py`'s `_select_diverse_builds(ranked_order, pool, max_builds)`: picks the final set of builds to return by walking the already-best-first ranked order (from the LLM, or the deterministic fallback) and greedily preferring a build that doesn't repeat an already-chosen CPU, then one that doesn't repeat an already-chosen GPU, only falling back to a repeat of either once there aren't enough distinct options left to fill every requested slot. `recommend()`'s final-selection line now calls this instead of simply slicing the top `max_builds` off the ranked list.

**Root cause (live-reported: "the 3 build suggestions are still basically the same, but some pieces are changed out for each build"):** this is a direct side effect of the previous entry's fix. Sorting each category's candidates by relevance before the engine's `top_n` cutoff means a single best CPU/motherboard/RAM combination now legitimately and consistently rises to the top -- which is correct, but it also meant the highest-scoring handful of *builds* were almost always minor variations of that one combination (same CPU/motherboard, different storage pairing or cooler), never genuinely different hardware.

**Assumptions:**
- **CPU diversity takes priority over GPU diversity**, not the other way round, and no other category (RAM/storage/PSU/case/cooler) is considered at all. CPU is the single most defining, highest-visibility choice in a PC build; trying to diversify every category at once would fight against *also* wanting each build to still be a good fit for the stated requirements, and was judged to produce confusing, less-explainable results for comparatively little benefit over CPU+GPU alone.
- **Diversity is enforced as a hard greedy preference, not blended into `deterministic_score`** (which still ranks purely on fit/preferences, unchanged). Folding "is this CPU already used?" into the score itself would have made the score's own meaning harder to explain on the "What does the score mean?" guide panel already shown in the UI -- diversity is deliberately a separate selection step applied *after* scoring/ranking, not a scoring factor.
- **Falling back to a repeated CPU/GPU is preferred over returning fewer builds than asked for.** A small or narrow inventory (e.g. only one compatible CPU at all) should still get `max_builds` suggestions when that many valid builds exist, even if they can't all be genuinely distinct.

**Known risks / weaknesses:**
- This only diversifies the *final* selection, not the pool the LLM ranks from (still the top `pool_size = max(max_builds * 3, 10)` by deterministic score). If every build in that pool shares the same CPU, there's nothing left to diversify toward even though a different CPU might exist further down the full candidate list. Not hit in practice with a `top_n`/`pool_size` this size against the current 210-component seed, but a narrower inventory than that could still see non-diverse results for this reason.
- The ranking LLM's `reason` text is still written for whichever single build it was ranking, with no awareness that `_select_diverse_builds` might reorder or substitute afterward -- a `reason` could occasionally read a little oddly ("this build offers the most VRAM" on a build that's present *because* of CPU diversity, not because it topped every criterion). Judged a minor, rare cosmetic issue, not worth a prompt change for.

**Tests covering it:**
- `backend/tests/test_pipeline.py` (4 new tests): a repeated CPU is skipped in favor of a different one when one exists further down the ranked order, while still respecting rank order as the tiebreaker; falls back to repeats (never returning fewer builds) when the inventory has no real variety at all; GPU diversity kicks in as the secondary signal when CPU genuinely can't vary; a full end-to-end `recommend()` call with 3 equally-valid, distinct CPUs available asserts the 3 returned builds actually use 3 different CPUs, not the same one three times over.
- `ruff check`/`ruff format --check`/`pytest --cov` green: 221 tests, 96% overall coverage, `pipeline/recommend.py` at 99%.

## 2026-11-02 – Fetch and clean the actual page for extraction, not just its search snippet

**Generated:**
- `backend/app/search/page_fetch.py`: `HttpPageFetcher`/`PageFetcher` (a `Protocol`, same pattern as `search/client.py`'s `SearchClient`, so tests never make a real HTTP request -- SPEC.md §9.1). `/api/components/extract` (`routers/components.py`) now fetches the *chosen* search candidate's actual page (not the others, to keep this to one extra request) with `httpx`, strips `script`/`style`/`nav`/`header`/`footer`/`noscript`/`svg`/`form` tags with BeautifulSoup, and takes the remaining visible text (capped at `PAGE_FETCH_MAX_CHARS`, default 8000 characters) as extraction context -- prepended ahead of the existing short snippets, which stay as a fallback/supplement rather than being dropped.
- New settings: `FETCH_FULL_PAGE` (default true, an escape hatch back to snippet-only behavior), `PAGE_FETCH_TIMEOUT_S` (8s), `PAGE_FETCH_MAX_CHARS` (8000).
- `pyproject.toml` gains `beautifulsoup4` as a core (not dev-only) dependency -- it's used at request time, not just in tests.

**Root cause (live-reported: "the sites it recommends from have pcie power connector information, but it does not get extracted"):** a SearXNG search result's `snippet` is a short preview the search engine itself generated (often the page's meta description), not the page's actual content -- it was never a prompt-engineering problem, the LLM genuinely never saw the information at all. Confirmed directly against a real page during this fix: fetching `techpowerup.com`'s GeForce RTX 2060 spec page returns "*draws power from 1x 8-pin power connector*" and its physical dimensions in the cleaned text, neither of which SearXNG's snippet for that same page ever included.

**Assumptions:**
- **Only the chosen candidate's page is fetched, not every `other_candidate`'s.** Fetching N pages per extraction request would add N round-trips of latency to a single user action; the chosen result is the one the user already judged most relevant, and the existing merged-snippets behavior (2026-10-31's entry) still covers anything only a different result's *snippet* happens to state.
- **A fetch failure (timeout, 404, non-HTML content type, blocked by the site) is silent, not an error** -- `extract_component_specs` simply falls back to exactly the snippet-only behavior that already existed before this change. This was judged the right trade for a best-effort enhancement layered on top of an already-working flow: a page that can't be fetched shouldn't make extraction worse or fail outright, only as good as before.
- **8000 characters was chosen empirically**, not from a stated requirement: large enough to comfortably include a spec table/section on real hardware-database pages (confirmed on the TechPowerUp example above, where the power-connector sentence appears within the first 2000 characters of cleaned text), small enough to stay a reasonable addition to the LLM prompt's size/latency.

**Known risks / weaknesses:**
- Some sites render their spec table via client-side JavaScript; a plain HTTP GET + static HTML parse (no headless browser) won't see content that only exists after JS execution. Not handled -- would need a much heavier tool (e.g. Playwright-driven rendering) to fix, judged disproportionate for this project's scope. `search/client.py`'s own domain exclusions already bias results toward simpler, spec-table-style sites (TechPowerUp, manufacturer pages) over heavier retail/marketplace pages, which helps in practice.
- No robots.txt handling or rate limiting on this new outbound request -- acceptable for a single-user tool making one fetch per manual add-component action, but worth knowing if this code were ever reused somewhere higher-volume.
- `get_text(separator="\n", strip=True)` keeps some residual chrome on some pages (e.g. "Report an Error", breadcrumb-style labels) alongside the real spec text -- harmless noise for the extraction LLM to skip past, not attempted to filter further.

**Tests covering it:**
- `backend/tests/test_page_fetch.py` (6 tests): script/style/nav/footer text is excluded while real content and a value needed for extraction survive; truncation to the configured `page_fetch_max_chars`; a connection error, an HTTP error status, and a non-HTML `content-type` all return `None` rather than raising; `fetch_full_page=False` skips the request entirely.
- `backend/tests/test_api_llm_endpoints.py` (2 new tests): the fetched page's text (containing a PCIe connector line the snippet alone never had) actually reaches the extraction prompt, ahead of the short snippets; a failed fetch (`None`) falls back to the pre-existing snippet-only behavior without error.
- A real page (`techpowerup.com`'s RTX 2060 spec page) was fetched and manually inspected during this fix to confirm the cleaned output is genuinely useful, not just passing mocked assertions.
- `ruff check`/`ruff format --check`/`pytest --cov` green: 217 tests, 96% overall coverage.

## 2026-11-02 – Diagnosed and fixed a live "cannot save builds" bug: stale table columns

**Generated:**
- `backend/app/bootstrap.py`: `_sync_missing_columns()`, run right after `Base.metadata.create_all()` on every container start. It inspects each mapped table's actual database columns, compares them against the current model, and issues `ALTER TABLE ... ADD COLUMN` for anything the model has that the table doesn't -- never drops, renames, or alters an existing column, only ever adds one.

**Root cause (live-reported bug: "I cannot save builds now. When I click the save build button it blinks shortly and the builds tab shows 'an unexpected server error occurred'"):**
- This project has no migration framework (Alembic) by design (see the 2026-10-19 Phase 1 entry) -- `create_all()` only creates *missing tables*, it never alters one that already exists. `SavedBuild.purpose` was added to the model in a later commit than the one that first created the `saved_builds` table on the student's home-server deployment. Every restart since then kept calling `create_all()`, which correctly saw the table already existed and did nothing -- so the live table never gained the `purpose` column the code had been writing to and reading from for several commits. Every `INSERT`/`SELECT` touching it failed at the database level, surfaced to the frontend as a 500 ("unexpected server error"). This was never caught by any test because every test's database is created fresh via `create_all()` on an empty schema, which always gets the *current* model's full column set -- the bug only exists on a database that persisted across a schema change, which no test fixture does.

**Assumptions:**
- A real migration tool (Alembic) was deliberately not introduced this late to fix this -- `_sync_missing_columns()` is a scoped, additive-only stand-in that solves the one failure mode this project has actually hit (a new nullable column on an existing table), not a general schema-migration solution. It does nothing for a renamed/retyped/dropped column, which would need a real migration tool or a manual fix.

**Known risks / weaknesses:**
- This fix only self-heals on the *next* container restart after pulling the new code -- it doesn't retroactively fix a database the backend is currently running against without a restart.
- Column types are generated via `column.type.compile(dialect=engine.dialect)`, which is correct for every column type this project currently uses (String/Integer/Text/Boolean/DateTime/the custom non-native SAEnum), but wasn't exhaustively tested against every SQLAlchemy type that could theoretically be added later.

**Tests covering it:**
- `backend/tests/test_bootstrap.py` (2 new tests): a table manually created with an older, narrower column set than the current model gets the missing column added, existing rows survive untouched, and the new column reads back as `NULL`; a table that's already fully up to date is confirmed to be a true no-op (doesn't raise, doesn't duplicate anything).
- `ruff check`/`ruff format --check`/`pytest` green (201 tests at the time of this entry).

## 2026-11-02 – Era-aware hardware requests, and the real reason recommendations always reused the same parts

**Generated:**
- **The actual root cause of "the assistant always recommends the same hardware,"** reported live with logs showing the same CPU+GPU pair chosen for "play [a game]", "pick hardware from 2010 or earlier", and "look for a build with older hardware" alike: `compatibility/engine.py`'s `generate_builds()` only ever looks at the first `top_n` (default 5) candidates per category, *in whatever order it's handed them* -- its own module docstring already said sorting by relevance before calling it is the caller's job. `pipeline/recommend.py`'s `prefilter_candidates()` never did that sort; it just appended rows in plain database order, which in practice is insertion order. Since the original ~10-CPU demo seed was inserted before the 135 later-added historical/server CPUs (2026-10-31's seed expansion), `top_n=5` permanently saw only the first five CPUs ever inserted -- always the same modern parts -- no matter what was actually asked for. Confirmed directly: `db.query(Component).filter(category==CPU).all()` on the real 210-component seed returns ids `1, 9, 10, 11, 12` first, out of 37 CPUs.
- **Fix: `prefilter_candidates()` now sorts each category's candidates by relevance before handing them to the engine** (`_sort_candidates_by_relevance`), instead of leaving them in whatever order the database returned. This alone fixes the general bug for any stated preference, not just era (e.g. `min_vram_gb`/`min_cpu_cores` overshoot now also affects which candidates survive the `top_n` cutoff, not just the final ranking).
- **A genuinely new capability, not just the bug fix: `release_year` on every component** (`ComponentBase`/`Component`/`CandidateComponent`), so "hardware from 2010 or earlier"/"my newest gear" can be answered with real data instead of the LLM guessing. `ProjectRequirements` gains `max_release_year`/`min_release_year` (hard bounds, for an actual stated year) and `prefer_oldest`/`prefer_newest` (a relative preference, for "the oldest I have" -- the LLM is explicitly told never to invent a year for this case, since it doesn't know what's in the inventory). `_meets_hard_requirements` now drops any component (of any category) outside a stated year bound, missing data counts as failing, same policy as every other hard requirement. `deterministic_score` gained a matching soft nudge using the build's newest core component's year. The ranking and chat-reply prompts/payloads now include each build's cpu/gpu `release_year` so the LLM can actually reference real years instead of guessing or contradicting itself (the live log showed exactly that: "your builds use...2019" immediately after already claiming they fit "2010 or earlier").
- `backend/app/seed.py`'s 210 components all got a `release_year` (the historical/era ones already had an implied year in their `notes`; the rest are the real-world release year of that specific product).
- Surfaced through to the frontend: `ComponentSummary`/`InventoryView`/`RecommendView`/`BuildsView` all show each component's release year now, partly so this fix is actually visible/verifiable in the UI, not just in logs.

**Deliberate deviation from SPEC.md, flagged the same way others have been:** §4.2 doesn't define a `release_year` field on any component. Added anyway, as `ComponentBase` metadata rather than inside any category's spec class, since it's a property of the specific product, not a technical capability -- judged necessary to honestly answer a class of request the student actually hit live, not a speculative addition.

**Assumptions:**
- **`max_release_year`/`min_release_year` are hard requirements across every category, not just the one the user seems to be talking about.** "Hardware from 2010 or earlier" is read as "the whole build", not "just the CPU" -- a 2024 GPU paired with a 2008 CPU wouldn't honestly satisfy that request. This does mean a component with no recorded release_year is excluded the moment *any* era constraint is stated, same policy as a missing spec already failing `min_vram_gb` etc.
- **A build's "era" for the `prefer_oldest`/`prefer_newest` soft nudge is its newest core component's year** (max across cpu/motherboard/ram/gpu), not an average -- a build is only as modern as its newest part, so this was judged the more honest single signal, at the cost of not rewarding a build for having *several* old parts if even one part is recent.
- **A bug in the same family was found and fixed while making this change**: `services/backup.py`'s `_COMMON_COLUMNS` was a hand-maintained list of `ComponentRead` fields for the `.xlsx` backup format, already out of sync with the schema the moment `release_year` was added (it silently dropped the field on every backup round-trip, which then failed the sha256 integrity check). Changed to derive the column list from `ComponentRead.model_fields` directly instead of hand-maintaining a parallel list -- this exact class of bug (a model gains a field, a sibling hardcoded list/table doesn't know about it) is also what caused the `purpose` column bug fixed in the previous entry, so it's now fixed at the source for this specific list rather than patched again next time a field is added.

**Known risks / weaknesses:**
- The web-search/LLM extraction flow (`/api/components/extract`) does not attempt to fill in `release_year` -- it's manual-entry only, the same scope boundary `manufacturer` already has in that flow. A component added via search+extract still needs its release year typed in by hand on the Inventory tab if era-based requests should be able to use it.
- This only helps components that actually have a `release_year` set. Pre-existing rows already in a live database (seeded before this change, or added manually without it) will have `release_year = NULL` until re-seeded or edited -- the "Clear inventory" + "Populate with demo data" buttons (issue #1, previous entries) are the practical way to pick up the updated seed data's years on an already-running deployment.

## 2026-11-02 – "Clear inventory" and "Populate with demo data" buttons (issue #1)

**Generated:**
- `POST /api/components/clear` (`routers/components.py`): requires `{"confirm": true}` (400 otherwise, same pattern as `POST /api/backup/restore`), then deletes every `Component` **and** every `SavedBuild` in one transaction and returns `{deleted_components, deleted_builds}`. Builds are included because a saved build only makes sense in terms of components that still exist -- clearing the inventory out from under it would leave a build pointing at nothing.
- `POST /api/components/reseed` (`routers/components.py`): requires `{"confirm": true}` the same way, then walks `SEED_COMPONENTS` (`app/seed.py`) and inserts only the ones not already present, matched by `(category, name)` against the current inventory -- so it adds the demo data on top of whatever's already there (as requested) and is safe to click more than once: a second click adds nothing new. Returns `{added, skipped}`. `seed.py`'s own insertion logic (`specs_source=SpecsSource.MANUAL, specs_verified=True`) was pulled into a small `_component_from_seed_item()` helper so the container-startup `seed()` and this endpoint share it instead of duplicating it.
- `InventoryView.jsx` gains two buttons above the component table ("Populate with demo data" / "Clear inventory"), each gated by a native `window.confirm()` -- the same pattern already used for single-component delete and backup restore, not a new custom modal -- and reporting the result via `window.alert()`, matching restore's existing UX. Both are disabled while either is in flight.
- `schemas/components.py` gains `ClearInventoryRequest/Response` and `ReseedRequest/Response`.

**Assumptions:**
- **Confirmation is required for both actions, not just the destructive one.** Reseed is additive, not destructive, so technically doesn't need a confirm gate the way clear does -- but the user asked for "a confirmation step as well" right after describing both buttons together, and a consistent `confirm: true` requirement on both (mirroring the existing restore endpoint) was simpler than making the two buttons behave differently for a low-cost extra click.
- **Clearing the inventory also deletes all saved builds** (explicit decision from the user, asked directly rather than assumed) rather than leaving them with dangling component references. Note this is a deliberately bigger blast radius than restoring a backup, which replaces components but never touches saved builds.
- **Reseed's "already present" check matches on `(category, name)` only**, not full spec equality -- a component that happens to share a seed item's exact name and category (e.g. a manually re-added "AMD Ryzen 5 3600") is treated as "already seeded" and skipped, even if its specs/condition/quantity differ. Judged the right trade for "add what's missing" semantics; a stricter full-equality match would instead re-add near-duplicates whenever any field differs, which seemed more surprising.

**Known risks / weaknesses:**
- Clearing the inventory down to 0 rows interacts with the idempotent startup `seed()` call in `app/bootstrap.py`'s entrypoint flow: if the container restarts after a manual clear, `seed()` will auto-reseed from scratch (table is empty => not idempotent-skipped). Not a bug, but worth knowing if an empty inventory is deliberately being tested across a restart.
- Neither endpoint is behind any auth (consistent with the rest of this single-user exam project) -- `POST /api/components/clear` is a real, unguarded "delete everything" endpoint if the API is ever exposed beyond localhost/the home LAN.

**Tests covering it:**

- `frontend/e2e/inventory.spec.js` (3 new tests): clearing sends `{confirm: true}` and reports the result via both dialogs; declining the confirmation sends no request at all; reseeding sends `{confirm: true}` and reports its result.

## 2026-10-31 – Seed data expanded to 210 components across three hardware eras

**Deliberate deviation from SPEC.md, not flagged at the time -- corrected here:** §12 ("Uden for scope") explicitly excludes *"servere i rack-format"* (rack-format servers). This entry's seed data adds rack-mountable cases, rack motherboards, and single-socket server CPUs (Xeon E/Silver, EPYC 4004/7002) without flagging that against §12, unlike every other deviation in this project, which gets an explicit note at the time. Flagged now, after the fact: the student asked for "server specific hardware, like rack-mountable cases and motherboards" directly, so this is a knowing, student-directed choice to widen scope, not an oversight -- it's being named here for the same reason the `.xlsx` backup format and the per-request backend choice are named in their own entries, so a reader of SPEC.md doesn't mistake the inconsistency for carelessness.

**Generated:**
- `backend/app/seed.py` grown from 75 to 210 components, requested because recommendations kept converging on the same handful of recent parts. The new 135 components span roughly 2005-2010 (Socket 775/939/AM2+/LGA1366, e.g. Pentium 4/D, Athlon 64 (X2), Core 2 Duo/Quad, Phenom (II)), the 2010s (LGA1155/LGA1150/LGA1151/AM3+/FM2+/first-gen AM4, e.g. Sandy Bridge through Coffee Lake Refresh, FX-8350/9590, Ryzen 7 1800X), and more 2020s/2026 high-end (RTX 4090/5090, RX 7900 XTX), plus single-socket server/workstation hardware: rack-mountable cases (1U/2U/4U), rack motherboards (ASRock Rack, Supermicro), server CPUs (Xeon E/Silver, EPYC 4004/7002), ECC RAM, datacenter GPUs (Tesla P4, RTX A2000), and NAS/enterprise drives.
- `backend/app/schemas/components.py`: `CpuSpecs`/`MotherboardSpecs`/`RamSpecs.memory_type` widened from `Literal["DDR4", "DDR5"]` to also accept `"DDR"`/`"DDR2"`/`"DDR3"` -- needed to honestly represent 2005-2010s hardware, which predates DDR4. Nothing else in the codebase hardcodes the old two-value set (`compatibility/rules.py`/`engine.py` only check list/set membership), so this was a pure widening with no other code changes required.

**Assumptions:**
- **No new schema fields were added for rack/server-specific concepts** (rack units, ECC, multi-socket boards). This project's compatibility model already assumes exactly one CPU per build, so "server motherboard" here means a single-socket board (Xeon E, one Xeon Scalable socket, one EPYC socket) -- true dual-socket server boards are out of scope, not represented. Rack cases/motherboards/PSUs reuse the closest existing field values (e.g. a 4U rack case's `supported_form_factors` includes `"EATX"`/`"ATX"`; a redundant hot-swap server PSU's `form_factor` is mapped to `"SFX"`, the more compact of the two allowed values) and spell out the approximation in that component's `notes` field rather than inventing new Literal values or schema fields for a seed-data-only need.
- **Sub-1GB-VRAM-era GPUs (e.g. GeForce 7800 GTX 256MB, 8800 GTX 768MB) omit `vram_gb` entirely** rather than rounding to 0 or 1, since `GpuSpecs.vram_gb` is an integer field and 0 would read as "no VRAM" rather than "below this field's granularity"; the exact figure is still in the component name. The GTX 580 (1.5GB) is the one exception, rounded down to `vram_gb=1` with a note, since some seed variety benefits from it having a comparable (if conservative) numeric value for VRAM-based rule checks.
- **ATI-branded cards (pre-2006 AMD acquisition) use `vendor: "amd"`**, the only available option for that hardware lineage in `GpuSpecs.vendor`'s `Literal["nvidia", "amd", "intel"]` -- noted explicitly on each such component rather than left unexplained.

**Deliberate deviation from SPEC.md, requested explicitly by the student:** §7.1 specifies a single JSON snapshot file (`inventory-<timestamp>.json`); §7.2.1 says the backup destination is chosen "exclusively via `.env`", no code changes to switch (already revisited in the previous entry — backend choice is now also per-request). **Generated:**
- `services/backup.py` rewritten: `export_snapshot(db)` still builds the same internal "snapshot" dict shape SPEC.md §7.1 describes (schema_version, created_at, app_version, component_count, sha256, components) plus a new `builds` key -- only the on-disk *encoding* changes. `_write_xlsx(snapshot)` produces a workbook with a `Metadata` sheet (the same five top-level fields as key-value rows), one sheet per `Category` (cpu/motherboard/ram/gpu/storage/psu/case/cooler) with columns for every `ComponentRead` field plus that category's own spec fields (introspected from `SPEC_CLASS_BY_CATEGORY`, so a schema change doesn't need a matching change here), and a `Builds` sheet. `_read_xlsx(data)` reverses this back into the same dict shape, so the rest of the restore logic (hash check, schema_version check, per-row Pydantic validation) is **unchanged** from before -- only `_read_backup`/`_write_xlsx`/`_read_xlsx` are new. `_read_backup(raw, name)` dispatches on the file extension, so backups created before this change (plain `.json`, no `builds` key) are still fully restorable.
- **Component ids are remapped on restore.** A saved build's `components` field references component ids by whatever id they had *before* the restore -- since the DB assigns fresh auto-increment ids to the restored components (unchanged pre-existing behavior), restoring a build's old id references verbatim would silently point at the wrong (or no) components afterwards. `restore_backup` now tracks an old-id→new-id map while inserting components (via `db.flush()` after each insert to learn its new id) and rewrites each restored build's component references through that map before inserting the builds.

Every other field type (str/int/bool/None, and ISO-string datetimes) is a native Excel cell type and needed no special handling.
- `LocalStorage.list()`'s glob now matches both `inventory-*.xlsx` and `inventory-*.json`, so pre-existing `.json` backups on disk don't just disappear from the list after this change.

**Assumptions:**
- **SCHEMA_VERSION stays at 1** rather than being bumped, since adding `builds` is additive and backward-compatible (an old backup simply has none) -- bumping it would have made every pre-existing backup fail `schema_version` validation and become unrestorable, which felt like the wrong trade for a change that doesn't actually require a hard break.

Run after Phase 5. A multi-agent code review found 10 confirmed findings across frontend and backend; all are fixed in this entry.

**Generated/fixed:**
- **`InventoryView.jsx` — the "Extract directly" button was dead under the default configuration.** The backend requires a `candidate` when `ENABLE_WEB_LOOKUP=true` (the default), but the button always called `extractComponent(name, null)`. - **`InventoryView.jsx` — name/specs could get out of sync.** `handleConfirmSave` read the *current* `searchName` state instead of the name at extraction time, and the search field wasn't locked during review. Fixed: the name is frozen in a separate `confirmName` state at extraction time, and the input field is disabled while a result is under review.
- **`InventoryView.jsx` — a race between concurrent search/extract calls.** A slower, already-superseded call could overwrite a newer result when it finally finished. Fixed with a simple request-sequence counter (`useRef`) that ignores responses from a call that's been superseded by a newer one.
- **`InventoryView.jsx` — manual add could silently drop fields.** The `category` dropdown always overwrote the specs JSON's `category`, and since no spec model has `extra="forbid"`, fields from a mismatched category disappeared silently. Fixed: if the JSON's `category` exists and differs from the dropdown, an error is shown instead of silently overwriting it.
- **`backend/app/main.py` — 500 errors were missing CORS headers.** `@app.exception_handler(Exception)` didn't behave as expected: FastAPI specifically moves a handler registered on the `Exception` type itself to `ServerErrorMiddleware`, which Starlette always places **outside** user-defined middleware (including `CORSMiddleware`) — found because my first fix failed a test that directly reproduced the failure scenario (see Known risks). The correct fix is a plain `BaseHTTPMiddleware`, added *before* `CORSMiddleware` (so it ends up inside CORS in the call stack), which itself catches exceptions and returns a normal `Response` object. At the same time, `OllamaClient`/`SearxngClient`'s `httpx` calls are now wrapped and raise `LLMUnavailableError`/`SearchUnavailableError` instead of leaking raw `httpx` exceptions — `call_llm_with_retry` now goes straight to the fallback on an unreachable Ollama (without wasting a retry attempt on a failure that won't fix itself), and `/api/components/search` returns a clean 503 on an unreachable SearXNG.
- **`BackupView.jsx` — concurrent destructive actions weren't prevented.** The `disabled` check only covered the row in progress; other "Restore" buttons and "Create backup now" were still clickable during an in-progress restore. Fixed with one global `activeAction` state that locks every action button while one is in progress.
- **`api.js` — error messages were shown with redundant quote marks.** `JSON.stringify(detail)` was used regardless of whether `detail` was already a plain string (which most backend errors are). Fixed to only stringify when `detail` isn't already a string.
- **`frontend/Dockerfile` — the build didn't use the committed lockfile.** `npm install` ran before `package-lock.json` was even copied in. Fixed: copy both files together and use `npm ci`.
- **`docker-compose.yml`/`Dockerfile` — the backend port was baked into the JS bundle at build time.** A `.env` change to `APP_PORT` without `docker compose up --build` left the frontend image with the old port, with no visible sign of why. - **`display_output_available` is the only rule with an extra argument (`headless`).** The other 14 rules don't know about the use case (that's Phase 3/the LLM's domain) — `engine.generate_builds()` itself takes a `headless: bool` parameter and only passes it to this one rule.
- **"Not applicable" (e.g. no GPU selected, or an AIO cooler in `cooler_fits_case`) is returned as `pass`,** not a fourth status. SPEC §6 lists only pass/fail/unknown, and "rule doesn't apply" is semantically closer to pass (it doesn't block) than unknown (there isn't missing data, the rule is just irrelevant).
- **Candidate order and the `top_n` limit are the engine caller's responsibility.** The engine takes candidates in the order it receives them and cuts at `top_n` per category — a relevance sort (e.g. "closest to the user's requirements") belongs to the Phase 3 pipeline, where there are actually requirements to sort by.
- **The PSU safety margin/base watt (`PSU_SAFETY_MARGIN=1.3`, `PSU_BASE_WATT_W=75`)** is now an env var, but is only passed to the `backend` container in `docker-compose.yml` — not verified against an actually running container in this session (same caveat as Phase 1 regarding `docker compose up`).

**Known risks / weaknesses:**
- `psu_has_gpu_connectors` compares power connectors with a `Counter` (accounting for a GPU that may require two 8-pin connectors), but assumes the PSU's `pcie_power_connectors` list is a flat list of all available connectors — if two PSUs in practice share a cable run, this is a simplification.
- `cooler_fits_case` only covers air coolers (as SPEC §6 asks for); AIO radiator size against the case's radiator support isn't checked, because `CaseSpecs` (§4.2) has no `max_radiator_mm` field. Worth mentioning at the exam if asked about AIO builds.
- The combinatorics in `generate_builds()` are `O(top_n^7 * (top_n + gpu_count))` in the worst case — with `top_n=5` this is manageable (a few hundred thousand combinations, each evaluation is a cheap comparison), but no actual performance test has been done against a ~200-component inventory, which SPEC §5 mentions as the target. Should be profiled in Phase 3, once the pipeline actually feeds the engine a realistic number of candidates per category.
- `storage_slots_available` checks `>= 1` free slot/port, not whether the slot/port is already "used" by another drive in the same build — relevant only if multi-drive builds are added later (see Assumptions).
